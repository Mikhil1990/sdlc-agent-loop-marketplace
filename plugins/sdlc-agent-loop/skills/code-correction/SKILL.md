# Code Correction

Native invocation: a deterministic script gathers context (diff, dependency graph, past
incidents), **you** — this conversation — write the safeguard patch yourself, and a
second deterministic script applies it on a branch, runs the sandbox tests, and opens a
PR only if they pass. This agent never merges; it only proposes. This replaced an
earlier version of this skill that shelled out to `agent-cli correct` (since retired — ADR 0180), which spawned a
*second*, separate `claude` CLI subprocess for both the patch-generation LLM call and
the correction pipeline — reasoning with none of this conversation's context.

**Repo profile:** if `.sdlc-agent*/AGENTS.md` exists at the repo root, read it first — it is the authoritative execution contract for this repository (build/test commands, local conventions) and, where it conflicts with anything else in this tree, this file wins.

## Prerequisites

- The target repo must be onboarded: `codebase-map.json` and
  `constitution/product/product-rules.md` must exist, and it needs an `incidents/*.md`
  postmortem folder for there to be anything to correlate against (see the
  `incident-learning` skill for the postmortem format).
- `agent-cli` must be installed from the pinned release wheel (**not** an editable checkout):
  `uv tool install "agent-platform @ https://github.com/Mikhil1990/sdlc-agent-loop-marketplace/releases/download/v0.7.1/agent_platform-0.7.1-py3-none-any.whl"`,
  and `gh` authenticated for the target repo. See
  [the plugin README § Prerequisites](../../README.md#prerequisites) for the full list
  (`codebase-memory-mcp`, `AGENT_PLATFORM_API_URL` / `_PAT`, an onboarded repo);
  `agent-cli doctor` checks them. `agent-cli context` and `agent-cli apply-patch` do no
  LLM/network call themselves — only git, the local codebase-map/product-rules/incidents
  files, and (for `apply-patch`) `gh`.
- A test command that actually validates the target repo (e.g. `dotnet test`, `pytest -q`,
  `npm test`). Without one, generate and show the patch but don't apply it — ask the user
  for the right test command if they haven't given one.

## Step 1 — gather context (deterministic, no LLM call)

```bash
uv run agent-cli context --local --repo-path /path/to/repo --output correction-context.json
# or --base/--head or --pr, same as the change-impact skill
```

If `past_incidents` in the resulting JSON is empty, stop here and tell the user: "No past
incidents implicated by this diff; nothing to correct." This agent only acts when there's
a concrete past incident to address, not on generic risk.

## Step 2 — write the impact report yourself

Follow the `change-impact` skill's Step 2 instructions to produce a Change Impact report
from the same context (you can reuse it if you already ran that skill in this
conversation). This is not a separate subprocess call — it's the same native reasoning,
now feeding the patch-generation step below.

## Step 3 — write the patch yourself (native reasoning, no subprocess)

A Change Impact Analysis has flagged this diff as risky because it touches files
implicated in one or more past incidents. Propose a minimal, concrete safeguard — e.g. a
regression test, a guard clause, a validation check — that addresses the cited incident's
root cause, not a rewrite of the feature, following the rules below.

The rules are the **single authored copy** of this agent's behavioural rules — rendered
here verbatim from `agent_core/agents/code_correction.py::SHARED_RULES` (ADR 0106), the
same text the retired subprocess path (`agent-cli correct`, ADR 0180) composed into its system prompt. "The
diff" and "the Product Understanding context" are the `git_diff` and `product_understanding`
fields of the Step 1 JSON; "past incidents" are its `past_incidents` (each with
`matched_files`); "the Product rules / constitution" is `product_understanding.rules`.

- Paths must be relative to the repo root and match files that already exist in the diff or the Product Understanding context — do not invent files.
- The "Product rules / constitution" section is the target repository's repo profile (`.sdlc-agent*/AGENTS.md`) — its authoritative execution contract (build/test commands, local conventions). - The target repository may be in any language or stack. Follow the test framework, layout and conventions visible in the diff, the impact report and the Product Understanding context — never assume a framework, build tool, or directory layout they do not show.
- Prefer adding or extending a test over changing production logic. Only touch production code if the incident summary shows no test would have caught it.
- Keep the patch small and reviewable — one concern, not a general refactor.
- Explain the patch in 2-4 sentences, naming the incident(s) addressed and why this patch would have prevented them.
- If you cannot produce a safe, targeted patch from the given context, give only that explanation of why, and propose no patch.

The subprocess path emits the diff as a fenced ` ```diff ` block and the explanation under
a `## Explanation` heading; here, instead, write the patch to a file (e.g.
`.code-correction-patch.diff` in the repo root) and the explanation (2-4 sentences) to a
second file (e.g. `.code-correction-explanation.txt`) for `agent-cli apply-patch` in Step 4.

If the target repo has its own `agent_core/prompts/code_correction/system.md`, follow
that instead of the rules above.

## Step 4 — confirm, then apply (deterministic, no LLM call)

**Show the user the patch and explanation before running anything.** This step mutates
the repo (new branch, commit, test run, push, PR) — treat it as the same kind of
hard-to-reverse action any other git-mutating command would be, and confirm first, the
same as you would without this skill. This conversational confirmation *is* the
human-in-the-loop gate for the native path — there's no separate `--require-patch-approval`
DB-approval-item flow here (the retired `agent-cli correct` subprocess path had one, ADR 0180),
because the gate is already this exchange with the user.

Once confirmed:

```bash
uv run agent-cli apply-patch \
  --repo-path /path/to/repo \
  --patch-file .code-correction-patch.diff \
  --explanation-file .code-correction-explanation.txt \
  --impact-report-file impact-report.md \
  --incident-titles "Payment retry outage" \
  --test-command dotnet test
```

This creates a `code-correction/<timestamp>` branch, applies the patch (`git apply
--check` first), runs the test command in the repo root, and only if it exits 0 does it
commit, push, and `gh pr create` — with a PR body citing the incident(s), the impact
report, and confirming tests passed. It always returns to the original branch afterward,
whether or not a PR was opened. If the patch doesn't apply, tests fail, or push/PR
creation fails, no PR is opened — the failure reason is in the printed JSON's `detail`
field, and the repo is left on the original branch.

## Step 5 — report the run

After `apply-patch` returns, record the run so it reaches the hosted run history
([ADR 0032](../../../docs/decisions/0032-all-surfaces-authenticate-through-the-hosted-app.md),
[ADR 0044](../../../docs/decisions/0044-native-skill-runs-report-through-an-authenticated-ingest-endpoint.md)).
Status comes from the `apply-patch` JSON:

- `status == "proposed"` → `--status succeeded --pr <number parsed from pr_url>`
- anything else (patch didn't apply, tests failed, push/PR failed) → `--status failed --error "<detail from the JSON>"`

```bash
uv run agent-cli report-run \
  --action code-correction --repo <repo dir name> --repo-path /path/to/repo \
  --status <succeeded|failed> [--pr <n>] [--error "<detail>"] \
  --started-at <ISO time you started Step 1> \
  --report-file impact-report.md --context-file correction-context.json \
  [--dossier-id <id>] [--packet-id <id>]
```

This skill has no admission step, so most invocations have neither id — omit both flags
and reporting behaves exactly as before. Only pass `--dossier-id` / `--packet-id` if the
user named one for this correction (unit D14,
[ADR 0107](../../../docs/decisions/0107-a-native-run-carries-the-admission-provenance-that-joins-it-to-its-work-request.md) §1) —
never ask for one, and never invent one from context.

This is best-effort — `report-run` always exits `0`, spooling to
`~/.agent-platform/spool/runs.jsonl` on any failure. Never let it block surfacing the PR
URL or the failure reason. Tell the user whether it reported
(`AGENT_PLATFORM_RUN_ID:` printed) or spooled (a `~/.agent-platform/spool/` warning); if
`AGENT_PLATFORM_PAT` isn't set it spools silently — mention
they can set it (from the web app's Settings screen) to see native runs in `/runs`.

## Output

Report the outcome plainly: whether a PR was opened (give the URL), or why not (patch
didn't apply, tests failed — show the tail of `test_output`, or no incident was matched).
Never claim a fix was "applied" or "merged" — this agent only proposes; a human approves
and merges the PR itself.

If the result carries a non-empty `profile_command_uninvokable` (unit D9, ADR 0098 §2/§3),
say so distinctly from an ordinary test failure: the test command itself could not run,
which means the repo profile is stale, not that the tests failed. Point at editing the
repo profile in the web app — never edit `.sdlc-agent*/AGENTS.md` directly, it is
overwritten on the next run.

The native path now records a run in `/runs` (Step 5). It still does **not** open a
trackable approval item — this skill is the only safeguard-patch path (`agent-cli correct` and
its `code_correction_pr` gate were retired by ADR 0180). Tell the user this if they ask why a
native PR isn't in `/approvals`.
