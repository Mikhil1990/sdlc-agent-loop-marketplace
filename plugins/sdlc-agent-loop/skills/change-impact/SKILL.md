# Change Impact Analysis

Native invocation: a deterministic script gathers context (diff, dependency graph, past
incidents), and **you** — this same conversation — write the Change Impact report
yourself, following the instructions below. This replaced an earlier version of this
skill that shelled out to `agent-cli impact`, which spawned a *second*, separate `claude`
CLI subprocess to do a single-shot LLM call. That subprocess call reasoned with no
access to anything you'd already learned in this conversation and its result came back
as an opaque string; doing the reasoning here means it can draw on this session's
context and you can be as good the underlying reasoning model actually is here, not
whatever the one-shot subprocess call produced.

**Repo profile:** if `.sdlc-agent*/AGENTS.md` exists at the repo root, read it first — it is the authoritative execution contract for this repository (build/test commands, local conventions) and, where it conflicts with anything else in this tree, this file wins.

## Prerequisites

- The target repo must be onboarded: `codebase-map.json` and
  `constitution/product/product-rules.md` must exist (run `uv run agent-cli onboard-repo
  --repo-url <url>` first if not).
- `agent-cli` must be installed in the environment running this skill, from the pinned
  release wheel (**not** an editable checkout): `uv tool install "agent-platform @ https://github.com/Mikhil1990/sdlc-agent-loop-marketplace/releases/download/v0.6.15/agent_platform-0.6.15-py3-none-any.whl"`.
  See [the plugin README § Prerequisites](../../README.md#prerequisites) for the full list
  (Python + `uv`, `codebase-memory-mcp` on `PATH`, `AGENT_PLATFORM_API_URL` / `_PAT`, an
  onboarded repo); `agent-cli doctor` checks them. Only `agent-cli context` is used here —
  it does no LLM/network call, just git + the local codebase-map/product-rules files.

## Step 1 — gather context (deterministic, no LLM call)

Pick the mode that matches what the user wants analyzed:

```bash
# Uncommitted local changes (diff vs HEAD)
uv run agent-cli context --local --repo-path /path/to/repo --output impact-context.json

# A local branch vs a base branch (e.g. still on main, comparing a feature branch)
uv run agent-cli context --base main --head test/breaking-change --repo-path /path/to/repo --output impact-context.json

# An open PR on the fork, via gh
uv run agent-cli context --pr 3 --repo-path /path/to/repo --output impact-context.json
```

If the user hasn't said which diff they mean, ask (uncommitted changes? a specific
branch/PR?) rather than guessing — `--local` and `--base main` produce very different
diffs.

If the command prints "No modified files found" (no `--output` file is written in that
case), relay that message to the user as-is — it includes fork-aware suggestions — and stop.

Read the resulting JSON (`git_diff`, `modified_files`, `product_understanding`,
`past_incidents`, `diff_meta`).

## Step 2 — write the report yourself (native reasoning, no subprocess)

You are doing Change Impact Analysis: given the git diff and Product Understanding
context (dependency graph + product rules), produce a precise pre-merge impact report in
Markdown, following the rules below.

The rules are the **single authored copy** of this agent's behavioural rules — rendered
here verbatim from `agent_core/agents/change_impact.py::SHARED_RULES` (ADR 0106), the same
text the subprocess path (`agent-cli impact`) composes into its system prompt. The
`agent-cli context` JSON is where "the provided context" lives: `git_diff`,
`modified_files`, `product_understanding` (edges, endpoints, entities) and `past_incidents`
(each with `matched_files`). "The product rules in the context" is
`product_understanding.rules`; "past incidents … their files" means an incident's
`matched_files`.

- The target repository may be in any language or stack. Infer its conventions from the provided context — never assume a framework, build tool, or directory layout the context does not show.
- The product rules in the context are the repository's repo profile (`.sdlc-agent*/AGENTS.md`) — its authoritative execution contract. Where it conflicts with a convention you would otherwise assume, it wins.
- Trace blast radius using provided edges, endpoints, and entities — do not invent files not in context.
- Flag breaking changes to DTOs, domain aggregates, schemas, API contracts, and integration events.
- Assign severity: 🔴 High (breaking API/contract/events/database schemas), 🟡 Medium (behavior change, non-breaking API), 🟢 Low (cosmetic/docs/refactoring).
- If past incidents are provided, and any of their files overlap the diff or blast radius, cite them by title/date in Recommended Actions (e.g. "Last time this changed, it caused ... — recommend ...") and raise severity if the diff touches an incident's root-cause files without addressing its recommended safeguard.
- A past-incidents entry with kind "known_unfixed" is not an incident: it is an error already known and left unfixed. Say "known unfixed error here (marked by <marked_by>, <date>)" for it, never "last time this caused" or a title-and-date citation, and do not raise severity for it alone.
- Be concise; prefer bullet lists over prose.

Write the report under these exact section headings (they exist for downstream parsing —
use them verbatim, in this order): `## Summary`, `## Severity`, `## Downstream API Impact`,
`## Database / Schema Impact`, `## Affected Files`, `## Recommended Actions`.

If the target repo has its own `agent_core/prompts/change_impact/system.md` (a
repo-specific override, e.g. this repo's eShop demo prompt naming .NET/EF Core/EventBus
specifics), read and follow that instead of the generic rules above — it takes
precedence for that repo.

If the user asked for a specific Detection Mode, apply it as an extra rule on top of the
above rather than replacing it: **Prefer Coverage** — flag borderline cases rather than
staying silent; **Prefer Precision** — only flag 🔴/🟡 when the diff/edges/entities give
clear, specific evidence. Default (no mode requested) is balanced judgment, as above.

After writing the narrative sections, append one more section verbatim from the gathered
context — do **not** re-derive these numbers yourself, they're computed deterministically
(not an LLM guess) so they must match exactly what `agent-cli context` returned:

```
## Deterministic Blast-Radius Score

- **Blast radius:** {product_understanding.blast_radius_score.blast_radius} related file(s) reachable from the diff
- **Severity:** {blast_radius_score.severity_label} (max whole-map degree among modified files: {blast_radius_score.severity_score})
- **Keystones touched:** {comma-separated `file` (degree N) from blast_radius_score.keystones_touched, or "none"}
- **Confidence notes:** (bullet each entry in blast_radius_score.confidence_notes, omit this line if empty)
- **Incident correlation blind spots:** (bullet each entry in the context JSON's top-level `incident_blind_spots` list, omit this line if empty)
```

Write the finished report (narrative + this appended section) to `impact-report.md` in the
repo root (or the path the user asked for) using the Write tool.

## Output

Surface the report to the user directly (it's already formatted Markdown) rather than
re-summarizing it — the severity markers and section headings are meant to be read as-is.
Mention the saved file path so the user can find it afterward. If the report cites a past
incident, offer the `code-correction` skill as the follow-up ("want me to propose a
safeguard PR for that?") rather than opening one unprompted.

## Step 3 — report the run

After the report is written, record the run so it reaches the hosted run history
([ADR 0032](../../../docs/decisions/0032-all-surfaces-authenticate-through-the-hosted-app.md),
[ADR 0044](../../../docs/decisions/0044-native-skill-runs-report-through-an-authenticated-ingest-endpoint.md)).
This is best-effort by construction — `agent-cli report-run` always exits `0`; if it
can't reach the backend it spools to `~/.agent-platform/spool/runs.jsonl` and retries on
the next call. **Never let this step delay showing the user the report from Step 2.**

```bash
uv run agent-cli report-run \
  --action change-impact --repo <repo dir name> --repo-path /path/to/repo \
  --status succeeded --started-at <ISO time you started Step 1> \
  --report-file impact-report.md --context-file impact-context.json \
  [--dossier-id <id>] [--packet-id <id>]
```

This skill has no admission step, so most invocations have neither id — omit both flags
and reporting behaves exactly as before. Only pass `--dossier-id` / `--packet-id` if the
user named one for this analysis (unit D14,
[ADR 0107](../../../docs/decisions/0107-a-native-run-carries-the-admission-provenance-that-joins-it-to-its-work-request.md) §1) —
never ask for one, and never invent one from context.

Then tell the user which happened:
- `AGENT_PLATFORM_RUN_ID:<id>` on stdout → reported; the run is in `/runs`.
- a stderr warning about `~/.agent-platform/spool/` → spooled, will flush on the next run.
- nothing printed and no warning → `AGENT_PLATFORM_PAT` isn't
  set, so it spooled silently. Mention the user can set it (from the web app's
  Settings screen) to see native runs in `/runs`.
